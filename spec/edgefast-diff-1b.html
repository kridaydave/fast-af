EdgeFast‑Diff 1B · a block‑diffusion hybrid

Maximum single‑stream tokens per second from a 1B model, without shipping garbage.

Params

A 1B model with a mostly delta‑rule backbone and block‑diffusion decoding. It attacks speed from two directions: a per‑pass read that does not grow, and several tokens revealed per pass. Quality is guarded by pass@1 on HumanEval, tracked at every step.

Part I · Goal

What this is for

One target: the fastest single‑stream output that still solves coding problems. Speed with garbage answers wins nothing.

The governing formula. Speed comes from two levers: read less data per step, or emit more tokens per step. This spec pulls both. 
TPS ≈ bandwidth ÷ bytes read per forward pass × tokens emitted per forward pass
  • Read less: a mostly delta‑rule backbone with no growing KV cache.
  • Emit more: block‑diffusion decoding reveals several tokens per pass.

Part III · Architecture

How the model is built

Mostly cheap delta‑rule layers, a few full‑attention layers for recall, spread evenly. A 3:1 ratio, attention every 4th block.

Component Choice Evidence
Linear (18) Gated DeltaNet (GDN) Delta‑rule layers win recall: GDN‑2 > GDN > KDA > Mamba‑3 > Mamba‑2 at 1.3B (arXiv:2605.22791). GDN ships in Qwen3‑Next; kernels exist.
Attention (6) Full attention, GQA 4 KV heads, head dim 128, NoPE 3:1 ratio, uniformly interleaved at blocks 4, 8, 12, 16, 20, 24. Recall saturates at 3:1 (arXiv:2507.06457). Sliding window retracted: windowed hybrids degrade past the window (arXiv:2406.07887).
Placement Uniform interleave No ordering beats evenly dispersed.
FFN SwiGLU, 8/3 expansion Standard.
Norm RMSNorm, pre‑norm Standard.
Vocab / emb 32k, tied Small table at 1B.
Train context 32k Mamba state unbounded at constant cost; attention caches the prompt once.
Precision int4 QAT from the start ~0.5‑2pt quality cost for ~2x bandwidth ceiling.

Part IV · Decoding

Block‑diffusion decoding

Fill in a block of 32 masked slots over 8 to 16 steps, revealing 2‑4 tokens per forward pass. Speed lives in the decode policy, not the architecture.

  • Block size 32. LLaDA and the fixed‑state paper both converge on 32 masked slots.
  • 8‑16 denoising steps. About 2‑4 tokens revealed per pass. Not LLaDA's 512‑step config, which is 1 token per pass and slower than AR.
  • Unmasking. Parallel, confidence threshold 0.9 (Fast‑dLLM style), not strict sequential ordering. The measured TPS wins live here.
  • Prompt cache. Prompt encoded once and cached. Attention layers cross‑attend the clean prefix; GDN layers carry a constant‑size state across blocks. Training computes the prefix the same way inference does, so the cache is exact.
Back of envelope (H100). 1B int4 ≈ 0.6 GB per pass, pass rate ~2,000‑3,000, times ~3 tokens per pass. Paper math says 6‑9k tok/s; expect about a third after overhead and remasking waste. The fixed‑state paper measured 297 tok/s single‑stream for a 3B pure‑Mamba block‑diffusion model at 256k context, 231 for the hybrid. That is the closest real datapoint.

Part V · Training recipe

Three stages

Pretrain, distill, then fine‑tune with reinforcement. Each stage has a budget and a known risk.

  1. Pretrain ~500B tokens. Code‑heavy mix (FineWeb‑Edu + code + math), block‑diffusion objective, block size 32, context 1024 then extend to 32k. The fixed‑state 3B trained on 300B with acceptable quality, so 500B at 1B is plausible.
  2. Distill ~100B tokens. From a strong coder teacher (Qwen3‑Coder class).
  3. SFT, then RLVR. Reward = tests pass. RL on diffusion likelihoods is immature (only LLaDA 1.5's VRPO and DiffuCoder's coupled‑GRPO published). DiffuCoder also made the model tolerant of halved denoising steps, so RLVR buys competence and speed.
Budget note. No paid teacher. Open synthetic code datasets (Magicoder, Evol‑Instruct‑Code) for SFT; execution‑feedback data (CodeFeedback) for reward signal. slime (THUDM) is the upgrade path for env‑based RL if GPUs are rented later.

Part VI · Benchmark week

Prove it before spending

Before any training, show the approach beats the competitor. If it does not, pivot early. Cheaper than training.

  1. Reproduce B0, B1, B2 on our hardware. These numbers are the whole scoreboard.
  2. Benchmark open diffusion models honestly. LLaDA‑8B (default + Fast‑dLLM decoding) and Dream 7B against Llama‑3 8B / Qwen3 8B on identical hardware. No independent head‑to‑head exists anywhere. If diffusion cannot win after tuning, pivot to B2 + competence training.
  3. Optionally run the fixed‑state authors' setup if code exists. Nearest proxy for D1.

Part VII · Hardware reality

What runs where

Benchmarks on Kaggle's 2x T4 (16 GB each, Turing, ~320 GB/s, no NVLink). Ratios carry over; absolute numbers do not.

  • No bf16, no AWQ. Full precision is fp16; quantized is GPTQ int4 or llama.cpp Q4_K_M. Turing misses Ampere+ attention kernels, so absolute TPS sits below the bandwidth math.
  • One benchmark per GPU. Tensor parallelism across PCIe‑linked T4s costs more than it gives at batch 1.
  • 8B models fit. Q4 is ~4.5‑5 GB. LLaDA‑8B via the diffuse‑cpp GGUF fork. EAGLE‑3 targets newer GPUs; B2 may need llama.cpp spec‑decode or older vLLM. Budget a day of friction.
  • Colab TPU excluded. The entire stack is CUDA. Porting decode loops to JAX/XLA to measure other people's models buys nothing.
  • Strategic: this project is PyTorch/CUDA. Training compute comes from rented A100/H100 hours.

Part VIII · Risks

What could go wrong

Known failure modes and their mitigations. Written down so nothing is discovered the expensive way.

Model risks

  • Few‑step quality cliff. Generative PPL degrades steeply below ~8 steps (15.3 at 4 steps vs 6.4 at 32). The 8‑16 range is a bet, not a fact.
  • Long‑context recall. Fixed‑state passkey scores weak at 16k for all mixers. The 3:1 ratio exists for this; watch it.
  • Adaptive steps per block. More steps for hard code, fewer for boilerplate. No paper makes this the headline. Either a trap or our edge.

Data risks

  • Benchmark contamination. HumanEval must stay out of all training data. Use MBPP or generated problems for reward; run n‑gram overlap checks; touch HumanEval only at final eval.
  • Code‑biased pretrain. A code‑heavy mix can spit code for "hello". Keep general text in the mix; rely on SFT for chat behavior; pilot run first.

Process risks

  • First‑time pretrainer. Pilot runs on small budgets first; understand each stage before running.
  • Vibe‑pretraining. Every run gets a written hypothesis, a metric, and a kill criterion before it starts. No blind runs on full budget.
  • Diffusion RLVR immaturity. Could block competence. Fallback: distillation‑only with a lower bar for v1.
  • Diffusion + tool calling. v1 stays single‑shot code RL: generate, sandbox runs it, reward from execution. Defer interactive RL to v2.
  • Process gate. Kriday must understand every part before work continues. No stage proceeds until explained and agreed.
